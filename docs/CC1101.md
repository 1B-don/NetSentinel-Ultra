## Implemented software

The existing receive adapter now supports an optional `cc_diagnose` callback. `NsCcBus` supplies an independently authored read-only SPI helper for that callback: identity, main state and raw RSSI. It uses status-read headers exclusively, never command strobes, writes or FIFO access. Identity is read twice; inconsistent reads report I/O failure. All-zero/all-one identity is rejected; unrecognized nonzero version values are retained rather than claimed authentic. State consistency has three bounded attempts. A chip-not-ready status or persistent state transition reports Timeout. Failed diagnostics leave the caller's output unchanged.

The helper follows the public [TI CC1101 datasheet](https://www.ti.com/lit/ds/symlink/cc1101.pdf). Status addresses need the read/burst header bits to avoid selecting their overlapping command strobes. RX state is 0x0d. RSSI conversion uses signed raw values; the helper retains half-dB resolution and requires an explicit offset. No universally calibrated offset is assumed for this board.

After successful detection, the receive wrapper idles, delegates frequency configuration/calibration/settling to `cc_receive`, then checks settled RX when diagnostics are available. RSSI samples additionally check RX state; an unexpected state, invalid RSSI or callback failure closes/releases the radio. Ports without raw diagnostics retain the prior callback path and must independently validate settled RX in `cc_rssi`; the UI reports raw diagnostics unavailable. No automatic power cycling, reset or transmit recovery is implemented.

Sessions sample at most once per 100 milliseconds, without blocking sleeps or missed-sample catch-up. First sample after successful tuning is immediate; the port must finish settling before returning success. A 64-sample ring drives the chronological signal plot, recent mean and percentage of recent samples at or above -80 dBm. Min/max covers all samples since tuning. Graph scale is fixed at -120 to -20 dBm, clipped at the ends. These are RSSI summaries, not decoded packets, occupancy estimates or proof of a signal source. The trace is indexed by samples; UI/I/O delays can extend its time span.

## Unified controls and storage

Select CC1101 from the dashboard, confirm the physical selector, then OK starts/stops reception through an installed port. Left/Right changes frequency by 100 kHz; Up cycles 315, 433.92, 868 and 915 MHz presets. Down toggles diagnostics/trace and refreshes diagnostics during RX. Diagnostics show the latest identity/state/raw RSSI snapshot and read count. Frequencies in silicon band gaps are rejected without disturbing an existing receiver. The concrete board port may reject further unsupported frequencies or presets.

Idle frequency selections use existing dual-slot persistent settings; settings format is unchanged. Live retunes are temporary for the current session, reset frequency-specific RSSI statistics/trace, and preserve total session observation count. Changing an idle frequency clears stale displayed measurements. A failed retune or diagnostic stops the session and records its result through normal history/SD handling. Wi-Fi/NRF/CC remain mutually exclusive application sessions, and the existing ESP scan gate is unchanged.

CSV keeps the existing seven columns. CC records include raw dBm samples, per-window threshold percentage, timing/threshold configuration, available diagnostic snapshots and live frequency-change events. Each record carries the session/time/frequency context. Logging failures stop/release reception; prior files are never overwritten. All storage tests use mocks, not the physical SD card.

## SDK integration still needed

Default Flipper CC capability remains false. The permitted API 87.1 SDK exposes generic `subghz_devices_*` declarations and enabled registry exports for lookup, begin/end, external connection status, frequency validity/setting, RX, RSSI, idle/sleep. It defines the external name `cc1101_ext`, but its external entrypoint `subghz_device_cc1101_ext_ep` is marked `Function,-` in the export table. Thus the SDK exposes a generic receiver interface, not a callable external-provider entry point or proof the provider is available to FAPs. Registry operations such as init/deinit, idle, set-RX and RSSI have no deadline parameter or error return; frequency setting returns a value but has no timeout contract. The SDK declarations alone therefore do not satisfy bounded initialization, cancellation, error recovery, external-only binding, or teardown requirements.

The public [Flipper Sub-GHz CLI implementation](https://github.com/flipperdevices/flipperzero-firmware/blob/dev/applications/main/subghz/subghz_cli.c) demonstrates the generic device-registry pattern, including lookup by the external-device name; the [public device API reference](https://developer.flipper.net/flipperzero/doxygen/devices_8h_source.html) describes its callable contract. This is an upstream interface/implementation reference, not source proof of the owner's Momentum build. The permitted Momentum SDK-only archive establishes that the generic symbols are exported, but it does not reveal which registry provider the installed Sub-GHz app resolves or prove its external-provider implementation. Thus the owner's test confirms the existing app selected its external mode and showed changing RSSI values; the exact Momentum call chain and its bounds remain unverified.

The portable adapter boundary now supplies explicit operation budgets: 100 ms probe, 500 ms tune/receive, 200 ms total diagnostics (each SPI transfer bounded to 20 ms), and 20 ms idle/RSSI calls. Deterministic mock implementations validate these budgets and verify release on timeout, absent device, contention, repeated sessions and user cancellation between bounded calls. These deadlines are contracts for future adapters; they do not make the generic SDK functions cancellable. The physical provider gate remains off until a permitted provider contract can enforce the budgets, prove external-only acquisition and restore hardware resources. No Ultra CS/GDO wiring or modem/filter preset is inferred, and there is no internal CC fallback.

Review automatic state transitions and packet settings to exclude entry into TX, not just explicit TX calls. Retuning must finish IDLE, calibration, RX entry and RSSI settling before success. The physical port must reject unsupported board frequencies and preserve SPI/UART/expansion/power state. These are remaining adapter requirements; absence of a signal source is not that dependency. The latest SDK build evidence is recorded in [BUILD_RESULT.md](BUILD_RESULT.md); the provider remains excluded from that artifact.

1. Ask the owner to set/confirm the CC1101 physical selector. Record application/SDK/device revisions and board context. Acquire explicitly external only; read stable identity/state and compare with the expected device register behavior.
2. Enter RX at supported preset frequencies. Record settled RX state, raw/converted RSSI, sample timestamps, CSV contents and trace. Ambient/noise-floor observations establish read/monitor behavior only, not calibrated sensitivity or successful reception of a known signal.
3. Exercise stop, idle, restart, busy ownership, unsupported frequency and SD failures; check bus/ownership/resource restoration. Never unplug/change the selector while a session owns the radio.
4. Leave formal reception/sensitivity/calibration tests pending until a suitable known signal can be observed. No transmission or signal-generator operation is authorized by this plan.
