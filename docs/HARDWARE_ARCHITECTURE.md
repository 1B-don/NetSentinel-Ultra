# Ultra V3 hardware integration architecture decision

Baseline: `4205b481d8aef69977152656acc03e3e3a301b54`. Target: permitted Momentum d3f89dfe SDK API 87.1 / target 7. Status: architecture/evidence review and software-only ownership regression tests; no new physical provider, diagnostic deployment or firmware change.

## Decision

Retain the typed, externally gated board adapter boundary. Prefer an existing reviewed external Sub-GHz registry provider for CC1101 if its installed-target lifecycle can meet the existing budgets. NRF24 has no identified exported managed receiver service; its direct HAL path still lacks bounded SPI acquisition. No evaluated architecture currently meets all reliability, cancellation, routing and passivity requirements for either physical adapter. Do not turn an architecture preference into an enablement flag.

The best long-term ownership architecture is a shared firmware-managed arbiter with finite reservation and typed receive-only operations, but no such NRF24 service or finite CC lifecycle is established by this SDK. Adding one requires a separate firmware/API project and is outside this milestone. Application-local plugins, queues and worker threads cannot create exclusive ownership against existing firmware clients.

## Verified SDK surface

Reviewed only permitted SDK headers: SPI public API/types/config, mutex, `lib/subghz/devices/devices.h` and `types.h`, the external CC interconnect header, plugin manager, and RPC application interface. Cross-checked enabled names in the supplied API table; provenance/checksums are in MOMENTUM_BUILD.md. No firmware implementation was read, and no dynamic provider was loaded.

- Generic external SPI handles share bus R with NFC/Sub-GHz. `SpiDefault` selects generic PA4 CS; `SpiExtra` selects PC3 CS; data/clock are PA6/PA7/PB3. Neither identifies the Ultra V3 nets. SPI acquire is void/blocking, with no timed/try-acquire/shared-lock accessor. Timed transfers begin after ownership; exposed callbacks do not provide finite reservation. Full analysis: NRF24_SPI_ACQUISITION.md.
- Enabled Sub-GHz registry APIs provide named device lookup and delegated lifecycle/RX/RSSI methods. `SubGhzDeviceInterconnect` contains callbacks, not a service message protocol or ownership lease. Begin returns bool; end, idle and RX setters return void. None carries a timeout/cancellation argument. Loading a plugin does not give its callbacks a deadline.
- The plugin ABI identifies `subghz_radio_device`, version 1. Plugin-manager alloc/load/get/free functions are enabled and filter application ID/API version. This verifies a loading interface, not plugin contents, external-only routing, installed availability, shared registry ownership or synchronization. ABI-version checks alone cannot establish the required hardware semantics.
- `subghz_device_cc1101_ext_ep` is disabled as a direct application import. That does **not** imply registry-based or supported dynamic plugin discovery is impossible. It means the FAP cannot directly import that symbol. No permitted installed provider implementation, exact package location/provenance or bounded lifecycle evidence has been supplied. Arbitrary plugin probing/loading is not a read-only radio diagnostic: loading can execute code, and begin/is-connect can have hardware effects.
- SDK RPC application callbacks/data exchange are generic application communication, not a documented NRF24/CC radio broker endpoint. No exported named NRF service or bounded radio reservation was found in the target table. RPC client timeout does not cancel a provider blocked in HAL acquisition.

## Ranked implementation paths

Ranking prioritizes reuse on the existing target without firmware changes. Every path remains conditional; none is authorized for physical execution.

| Rank / architecture | Compatibility and complexity | Reliability / cancellation | Performance | Firmware changes and present gate |
|---|---|---|---|---|
| 1. Existing external CC1101 registry/provider behind the typed adapter | Best supported CC abstraction; moderate integration after exact provider review; does not serve NRF24 | Must prove bounded begin/tune/RSSI/idle/end and external-only lookup, shared ownership and registry lifetime; ABI alone is insufficient | Suitable for current 100 ms RSSI cadence if provider bounds hold; no measured throughput | None if the existing provider already satisfies requirements. Missing permitted implementation and bound evidence; disabled |
| 2. Separate direct read-only diagnostic adapter using synchronized HAL ownership | Existing NRF probe and CC status helper are reusable; small diagnostic surface, moderate lifecycle work | Same SPI acquisition blocker as the full receiver. Read-only commands reduce mutation risk, not ownership wait. Needs prompt release/CS restoration and cancellation between finite calls | Four NRF register reads; bounded status transactions for CC; sufficient for communication checks, not RF validation | None only if an existing finite synchronized reservation can be established. No such contract found; routes unverified; disabled |
| 3. Existing firmware radio broker/service | Would give centralized ownership and preserve firmware arbitration; moderate client work if a verified service exists | Best design if service enforces leases, cancellation acknowledgement and teardown; current SDK does not establish this service | IPC overhead likely acceptable for RSSI; NRF dwell scheduling needs service-side support. No measurements or guarantees | An existing compatible service would need no change, but none identified. Creating one requires prohibited firmware changes; blocked |
| 4. Independent coprocessor/bridge with a typed numeric protocol | High complexity; new board route, power and provider requirements; cannot assume Ultra ESP32 connects to either radio | Could bound host communication, but peer-side operation/cleanup must also be bounded. Serial timeouts alone do not prove radio restoration | Extra latency; no routing or throughput evidence | Usually bridge firmware/hardware changes. Existing Marauder info UART exposes no verified NRF/CC service. Outside current scope; blocked |

Direct full RX over the present blocking HAL, detached workers, callback replacement, private lock casts, direct register/bit-banged access and bus reinitialization are rejected. They cannot meet synchronization/cancellation requirements and are not fallback architectures. An application plugin can package a driver without modifying firmware, but it still uses the same HAL and cannot repair absent shared-lock access. No alternate pin/bus mapping is proposed.

## Reference application patterns

The [public Sniffer driver](https://raw.githubusercontent.com/mothball187/flipperzero-nrf24/main/lib/nrf24.c) and [Sniffer app](https://raw.githubusercontent.com/mothball187/flipperzero-nrf24/main/nrfsniff/nrfsniff.c) use the generic SPI lifecycle. Existing review found its stop/finalization path invokes channel-finding that transmits. Reusable **interface pattern**: choose a supported handle, initialize, acquire, transact, release and restore. It provides no bounded-acquire contract and cannot be adopted as a receive-only lifecycle. No source was copied. The supplied static import report does not prove runtime pin selection, successful reception or cancellation behavior.

The [public upstream Sub-GHz CLI](https://raw.githubusercontent.com/flipperdevices/flipperzero-firmware/dev/applications/main/subghz/subghz_cli.c) illustrates registry initialization, named external lookup and lifecycle delegation. Its device-selection helper enables power and falls back to internal on a failed connection check. NetSentinel must omit those behaviors and reject a missing external device. This mutable upstream source is an interface reference, not evidence of installed Momentum implementation or bounded execution. The [public device API](https://developer.flipper.net/flipperzero/doxygen/devices_8h_source.html) corroborates delegation, not deadline semantics. Owner-reported external Read RAW/RSSI behavior is operational evidence for that app only.

The [manufacturer Ultra V3 guide](https://sacredlabstech.com/boards/ultra-v3/) describes the modules, external Sub-GHz UI and selector role. It supplies no revision-matched signal/net table in the reviewed text. No routing or SPI ownership guarantee follows from its application recommendations. The existing board remains the target; a new bridge is not presumed present.

## Separate diagnostic feasibility and shortest justified test path

A source-level standalone diagnostic is feasible, but an **enabled** diagnostic FAP is not currently justified. Keep the existing NRF read-only probe disconnected and the CC status helper behind its injected owned-bus contract. Do not build a physical diagnostic that merely relocates blocking acquire to a worker. Do not load a device plugin, invoke is-connect/begin, change settings, raise CE or enter RX just to discover whether it works.

1. Obtain a permitted, installed-target provider/ownership implementation or explicit supported contract proving finite shared acquisition and restoration. For CC include named external identity, registry init/deinit lifetime and begin/end effects; no internal fallback. For NRF resolve bus R finite reservation. Review plugin code/provenance offline before any load. If these cannot be provided without firmware changes, this target remains blocked.
2. Obtain revision-matched Ultra V3 SPI/CSN/CE/CS/GDO/selector/voltage documentation. An owner-approved power-off continuity check is an alternative input, not a task performed here. Preserve PA4/PC3 distinction; do not change Momentum settings to investigate it.
3. Implement and validate a separately gated diagnostic only after both gates close. NRF first test: four read-only register transactions with CE untouched, report plausible response only. CC first test: permitted bounded status reads with no reset, calibration, strobes or RX entry; the provider's initialization effects must also pass review. Chip-ready timeout and CS restoration are part of the CC transport. Stable results are communication evidence, not authentication, calibrated RSSI or RF reception.
4. Run full software/SDK/import checks, preserve known-good artifacts, then obtain separate owner approval of the exact diagnostic checksum, configuration and procedure before deployment/launch. Exercise cancellation only between finite calls and verify restoration/repeated operation. Physical selector changes require separate approval.

This is the shortest justified NetSentinel hardware path. Another existing-app UI observation cannot close the ownership blocker. No additional hardware test is requested or executed in this milestone.

## Software-only improvement

Expanded typed Flipper board tests inject Busy/I/O/Timeout/Cancelled acquisition results for NRF and CC, verify failed acquisition does not create ownership or release a foreign lock, and run 24 alternating start/contention/wrong-radio-release/cancel/repeated-stop cycles. They verify provider reuse, CE/frequency cleanup and balanced resource teardown across the actual Flipper adapter boundary. These are finite mocks, not SDK hardware guarantees. Runtime, UI, ESP information path, NRF probe and CC contracts remain intact. Full validation and exact undeployed artifact evidence are recorded in MILESTONES.md.
